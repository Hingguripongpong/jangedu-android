# 라이선스 검토 — Fairy-Stockfish(GPL-3.0-or-later)와 앱 전체의 관계

> 이 문서는 법률 자문이 아니다. 출시 전에 어떤 경로를 택하든 **라이선스 준수는 배포자(개발자)의 책임**이며,
> 소스 비공개를 원한다면 전문 법률 검토가 필요하다. 아래는 사실관계와 선택지를 정리한 것이다.

## 1. 사실관계 (현재 구조)

| 항목 | 내용 |
|---|---|
| 엔진 | Fairy-Stockfish `fairy_sf_14` (커밋 `f3e6969d…`), 라이선스 **GPL-3.0-or-later**, 소스 무수정 벤더링 |
| 결합 방식 | `libjanggi_engine.so` = Fairy-Stockfish + `engine_host.cpp` + `janggi_engine_jni.cpp`(이 저장소 코드). 앱 프로세스가 `System.loadLibrary`로 **같은 프로세스에 로드**하고 JNI로 함수를 호출 |
| 통신 | UCI 텍스트를 메모리 버퍼로 주고받음(파이프·소켓·별도 프로세스 없음) |
| 배포물 | APK/AAB 하나에 Kotlin/Compose 앱 코드와 `.so`가 함께 들어감 |

## 2. 왜 "엔진 + JNI 소스만 공개하면 끝"이라고 가정할 수 없는가

GPL은 프로그램을 "수정하거나 그 일부를 포함한 저작물(work based on the Program)"을 전달할 때 저작물
**전체**를 GPL 조건으로 라이선스하도록 요구한다(GPLv3 §5, §6). FSF의 GPL FAQ는 라이브러리를 동적으로
링크한 프로그램도 하나의 결합 저작물(combined work)로 보며, 정적/동적 링크를 구분하지 않는다는 입장이다.
반대로 "단순 집합(mere aggregation)" — 같은 매체에 독립 프로그램을 함께 담은 경우 — 은 GPL 적용 대상이 아니다.

이 앱의 구조는 다음 이유로 **결합 저작물로 해석될 가능성이 높은 쪽**에 있다.

* `.so`가 앱 프로세스 주소 공간에 로드되어 함수 호출(JNI)로 직접 연결된다.
* 앱의 핵심 기능(모든 합법수의 승률)은 엔진 없이는 동작하지 않는다 — 기능적 의존이 강하다.
* JNI 호스트 코드(`engine_host.cpp`)는 엔진 내부 심볼(`UCI::loop`, `Threads`)을 직접 호출한다.

"별도 프로세스 + 파이프(UCI)"로 통신하는 체스 GUI가 GPL 엔진을 "독립 프로그램"으로 다뤄 온 관행이 있지만,
현재 구현은 그 형태가 아니다. 따라서 **앱 전체(Kotlin/Compose 코드 포함)를 GPL 호환 라이선스로 제공해야
할 가능성을 전제로 계획**하는 것이 안전하다. 단정은 하지 않는다 — 결론은 법률 검토 사안이다.

## 3. 선택지

### 경로 A — 앱 전체를 GPL-3.0-or-later로 공개하고 Play Store에 출시(유료 포함)

* GPL은 **유료 판매를 금지하지 않는다**(§4 "You may charge any price or no price"). Play에서 유료 앱으로
  팔 수 있고, 다른 GPL 앱들이 실제로 그렇게 배포되고 있다.
* 의무: 바이너리를 받은 사용자에게 **대응 소스 전체**(앱 코드 + 벤더링된 엔진 + JNI 호스트 + CMake/Gradle
  빌드 스크립트)를 GPL 조건으로 제공. 실무적으로는 저장소 공개 + 스토어 설명과 앱 정보 화면에 URL 표기.
* 결과적으로 누구나 소스를 받아 재빌드·재배포(무료 배포 포함)할 수 있다. 이를 받아들일 수 있어야 한다.
* 저장소에 `LICENSE`(GPL-3.0 전문)를 두고, 각 소스 파일 또는 README에 저작권·라이선스 표기를 추가한다.
  `android/app/src/main/kotlin/com/example/janggiai/ui/about/AboutScreen.kt`의 문구를 "이 앱은 GPL-3.0-or-later로
  배포되며 전체 소스는 <URL>" 형태로 확정한다(현재는 엔진 부분만 서술).
* 앱 스토어 약관과 GPL의 충돌 여부(과거 다른 스토어에서 문제된 사례)는 Play 개발자 배포 계약을 직접
  확인해야 한다. 현재까지 Play에 GPL 앱이 다수 배포되고 있다는 사실은 참고 사항일 뿐 보증은 아니다.

### 경로 B — 앱 소스를 비공개로 유지하고 싶은 경우

* **출시 전 전문 법률 검토가 필요하다.** 결합 저작물 여부와 §5·§6 의무 범위를 임의로 판단하지 말 것.
* 구조 재검토 후보(어느 것도 자동으로 GPL 문제를 해소한다고 단정할 수 없음):
  * 엔진을 **별도 프로세스**(독립 실행 파일)로 실행하고 파이프/소켓 UCI로만 통신 — Android에서는 실행
    파일 실행 제약(W^X, targetSdk 29+)과 프로세스 수명 관리 문제가 있어 현재 인프로세스 설계를 택했음.
  * **비GPL 엔진**으로 교체 — 장기(9×10, 빅장/한수쉼) 지원 엔진 중 허용적 라이선스인 것은 드물다.
  * 자체 엔진(이 저장소의 Python 규칙엔진/탐색을 Kotlin·C++로 이식) — 기력 목표를 달성하려면 큰 작업.
* 검토 결과가 나오기 전에는 Play에 **프로덕션 출시를 하지 않는다**(내부 테스트 트랙까지는 배포로 볼 수
  있는지도 검토 대상).

## 4. 두 경로 모두에 공통되는 의무

* `THIRD_PARTY_NOTICES.md`, `licenses/GPL-3.0.txt`를 배포물과 저장소에 유지하고 앱 정보 화면에서 표시(현재 구현됨).
* 엔진 버전·커밋·SHA-256을 명시(현재 `FairyStockfishBuildInfo`, `engine/fsf.properties`, 단위 테스트로 일치 강제).
* 엔진 소스를 수정하면 수정 사실·날짜를 표기(§5(a)). 현재는 무수정.
* GPLv3 §6 "설치 정보(Installation Information)": 사용자 제품에 포함해 전달할 때 수정 버전을 설치할 수 있는
  정보를 요구하는 조항. 스토어 배포 앱은 사용자가 수정 빌드를 사이드로드할 수 있으므로 일반적으로 하드웨어
  판매자의 문제로 논의되지만, 이것도 법률 검토 항목에 포함할 것.
* 보증 부인(§15) 문구를 정보 화면·스토어 설명에 유지.

## 5. 지금 저장소의 상태와 남은 일

| 상태 | 항목 |
|---|---|
| 있음 | 엔진 소스·JNI 호스트·CMake·Gradle 스크립트 전체가 저장소에 포함 → 경로 A의 "대응 소스"는 이미 갖춰짐 |
| 있음 | 정보 화면의 엔진 고지, 제3자 고지, GPL 전문 에셋 |

| **없음** | 법률 검토(경로 B 필수, 경로 A도 권장) |
